从一张网页,到数据库里的一行

Seek 上一个岗位广告,怎么变成 FlowGT 数据库里的一行、 最后出现在会员的邮箱里。中间被动了哪些手脚。

主线例子

整份说明追同一个真实岗位,看它在每一站变成什么样子。

看那一行加粗的。'10h ago' 是给人读的, 1786398766 是给机器比较的。这一步就是整条链路的分水岭 —— 也是 2026-08-09 那次事故的所在。

七个阶段

1

决定抓哪些网址 URL planning

config.py · scraper.py:88 build_search_url · scraper.py:106 build_classification_url
7 个常量→最多 412 条网址

两条路。分类落地页是主路（2 类 × 8 页 = 最多 16 次加载,拿到那一类的全集）; 关键词是补网（33 词 × 3 地区 × 4 页 = 最多 396 次）。
为什么主次这么分:396 比 16 贵 24 倍,而且关键词会漏 —— 标题和正文里没有那 33 个词的岗位,关键词永远找不到。

daterange=1 = 只要 24 小时内的。这个数曾经是 7, 而邮件标题写着「今日岗位」—— 那就是 2026-08-09 事故。
2

真浏览器打开页面 headless browser

scraper.py:251 · Playwright + Chromium
网址→渲染完的 HTML

为什么非浏览器不可:Seek 的岗位是 JavaScript 画上去的。 服务器发回的第一份 HTML 里没有岗位,只有一段 JS。 纯 HTTP 抓取 → 0 张卡片;真浏览器 → 32 张。

2026-08-11 补的守卫:assert_real_page() —— 一张验证页不是「这一类没有岗位」。在它之前,101 个页面全部报「没有岗位」,工作流一路绿。
3

从 HTML 抠出字段 extraction

scraper.py:218 extract_job_cards
HTML→dict · 全是原文

入口是 [data-testid="job-card"] —— 它死了就全盘归零。 然后每个字段各有一条退路 fallback,因为 Seek 改过版。

一个匹配不到的选择器不会报错,只会安静地返回空字符串。 这是这一段所有问题的根源 —— 见下面的问题 2 和 3。
4

存进本地 SQLite local staging

scraper.py:48 job_id · scraper.py:69 save_job → jobs.db
dict→jobs.db 一行

身份用岗位号,不用整条 URL。Seek 的链接问号后面是每次搜索都不同的追踪码 —— 对整条 URL 取哈希,同一个岗位在 33 个关键词下会得到 33 个不同的 id。
真发生过:844 行里其实只有 244 个真岗位。

5

打包推给 API push

push.py · HTTP POST → /api/ingest/jobs
'10h ago'→1786398766

整条链路的分水岭。邮件的筛选条件是「36 小时内发布的」, 字符串没法比较大小。
关键设计:parse_age() 解析不出来时返回 None, 不是返回「现在」。以前解析不出就当成「刚刚」,于是一周前的岗位被当成今天的发出去。

宁可安静地少一条,也不要自信地错一条。
6

服务端归一化 + 落库 ingest & normalise

flowgt-website/functions/api/ingest/jobs.js
JSON · 全是原文→原文 + 判断

这一步给数据加判断,但原文永远保留。 归一化规则改了可以拿原文重跑;原文丢了就永远回不来。 这就是为什么表里同时有 title_raw 和 role_family。

一道闸门:isITRole() 信 Seek 自己的分类,不靠标题猜。
2026-08-10 实测:用标题猜的那一版,把 79 个来自 ICT 分类页的岗位拒掉了 34 个, 包括 Digital Graduate - Data and AI。
来源已经回答过的问题,不要用启发式再答一遍。
7

生产 D1 的一行 the fact row

migrations/0005-job-market.sql:32
原文 raw
title_raw company location_raw url — 抄来的,永不修改
判断 derived
role_family role_group seniority region — 算出来的,规则变了可重算
存活 lifecycle
first_seen_day last_seen_day is_open posted_at — 这个岗位的一生
first_seen_day 和 posted_at 不是一回事。
前者是我们第一次看见它的日子,后者是它发布的时刻。
2026-08-09 事故就是把这两个搞混了:第一次全量采集把过去一周的岗位一次性入库, 它们的 first_seen_day 全是当天,于是全部被当成「今日岗位」发出去。

四个已证实的问题

不是理论风险 —— 每一条都是拿库里的真数据数出来的。

1 · fetch_jd() 是死代码,JD 正文一个都没有

scraper.py:291 定义了它 · 全仓库 0 处调用 · jd 字段 0/155 行有值

后果:任何需要读岗位正文的功能都做不了 —— 包括 Radar, 因为 Radar 的全部前提就是「读正文,找出标题不提 AI、正文却在写 RAG 的岗位」。

2 · 主标题选择器已经死在 Seek 上

a[data-testid="job-title"]  →  ICT 页 0 个 · Sci-Tech 页 0 个 · 关键词页 0 个
退路 h3 a  →  32 · 17 · 8

整个抓取一直靠退路在跑。它没坏,但它在裸奔 —— 哪天退路也变了,就会像 08-11 那样安静地归零。

3 · job_type 永远是空的

job_type 有值的 0/155 · 两个选择器在 Seek 页面上都不存在

没有任何地方报错,因为「选择器匹配不到」返回的是空字符串,不是异常。

4 · 「Featured」岗位永远进不了邮件

posted_date = 'Featured'  4 行
→ parse_age 返回 None → posted_at 为 null
→ send-digest.js 硬条件 posted_at IS NOT NULL 挡住

Seek 的推广位不显示年龄。这是那个修法的代价,而且这个代价是划算的 —— 比起把它们当成「刚刚」发出去要好得多。但要知道它存在。

一个贯穿始终的形状

上面四个问题,没有一个会报错。

选择器失效
返回空字符串
函数没被调用
字段一直是空
时间解析失败
返回 None
被 Cloudflare 拦住
「本页没有岗位」
每一个失败,都被渲染成了一个看起来正常的结果。
这就是为什么这条链路上每一处都要有 audit,而不是等着它报错 —— 它永远不会报错。
